## 1. 引言

### 1.1 编写目的

本文档旨在详细说明"舆情研判系统"的软件需求，明确系统功能、性能、数据、接口等各方面的要求，为系统设计、开发、测试和验收提供依据。

本文档的预期读者包括：
- 项目管理人员：用于项目规划和进度控制
- 系统分析师：用于系统设计和架构规划
- 软件开发人员：用于编码实现
- 测试人员：用于编写测试用例
- 用户：用于需求确认和验收

### 1.2 项目背景

#### 1.2.1 项目来源

随着社交媒体的快速发展，微博、抖音等平台已成为公众表达意见和传播信息的重要渠道。海量用户产生的言论蕴含着丰富的社会情绪和舆论趋势。政府部门、企事业单位需要及时了解网络舆情动态，预测潜在风险，制定应对策略。

传统的人工舆情监测方式存在以下问题：
- **效率低下**：人工浏览和分析海量信息耗时耗力
- **覆盖面窄**：难以全面监控所有相关话题
- **主观性强**：依赖个人经验判断，缺乏客观标准
- **响应滞后**：发现问题时往往已错过最佳处理时机
- **缺乏深度**：难以挖掘深层观点和情感倾向

为解决上述问题，本项目开发了一套基于人工智能的自动化舆情研判系统，利用大语言模型（LLM）、向量数据库、自然语言处理等技术，实现舆情数据的自动采集、分析、研判和报告生成。

#### 1.2.2 项目目标

构建一个端到端的舆情分析与研判平台，实现：
- **自动化数据采集**：自动抓取微博等平台的热搜数据和用户评论
- **智能内容分析**：利用多Agent协同工作，深度分析公众观点和情绪
- **合规风险评估**：基于法规库进行内容合规性审查
- **趋势预测预警**：预测未来舆情发展趋势，提前识别风险点
- **专业报告生成**：自动生成结构化的研判报告（PDF格式）

#### 1.2.3 应用范围

本系统适用于以下场景：
- **政府部门**：网络舆情监控、社情民意分析、突发事件应对
- **企事业单位**：品牌声誉管理、危机公关预案、市场趋势洞察
- **研究机构**：舆论传播规律研究、社会治理数据分析
- **新闻媒体**：热点事件追踪、公众情绪监测

### 1.3 术语定义

| 术语 | 定义 |
|------|------|
| **LLM** | Large Language Model，大语言模型，如GPT-4、GLM-4等 |
| **Agent** | 智能体，具有自主决策和执行能力的AI模块 |
| **LangGraph** | 基于状态图的工作流编排框架，用于构建多Agent协作系统 |
| **RAG** | Retrieval-Augmented Generation，检索增强生成，结合向量检索和LLM生成 |
| **ChromaDB** | 开源向量数据库，用于存储和检索高维向量 |
| **Pydantic** | Python数据验证库，使用类型注解定义数据模型 |
| **WebSocket** | 全双工通信协议，用于服务器主动推送消息 |
| **ETL** | Extract-Transform-Load，数据抽取、转换、加载的统称 |
| **热搜词条** | 社交媒体平台的热门搜索关键词 |

| **舆情** | 公众态度和意见的总和 |
| **研判** | 研究判断，指对信息进行分析并得出结论的过程 |

## 2. 任务概述

### 2.1 项目目标

#### 2.1.1 总体目标

开发一套功能完善、性能稳定、易于使用的舆情研判系统，实现从数据采集到报告生成的全流程自动化，为决策者提供及时、准确、深入的舆情分析结果。

#### 2.1.2 阶段目标

**第一阶段（已完成）：基础平台搭建**
- 完成数据采集模块，支持微博热搜数据抓取
- 实现ETL数据处理流程，生成Top 20热点事件
- 开发5个AI智能体，实现多维度分析
- 构建Web前端界面，提供用户交互功能

**第二阶段（规划中）：功能增强**
- 扩展数据源，支持抖音、知乎、小红书等平台
- 增加情感分析粒度，支持更细粒度的情绪识别
- 优化报告可视化，增加图表和交互式展示
- 实现实时监控和告警功能

**第三阶段（规划中）：智能升级**
- 引入知识图谱，建立事件关联分析
- 开发预测模型，提升趋势预测准确性
- 支持自定义分析维度和报告模板
- 提供API接口，方便系统集成

### 2.2 用户特点

#### 2.2.1 目标用户群体

**主要用户**：
- **舆情分析师**：专业从事舆情分析工作的人员
  - 特点：具备数据分析能力，熟悉舆情分析方法
  - 需求：需要准确、全面、深入的分析结果
  - 使用频率：每天多次

- **政府决策者**：政府部门的领导和决策人员
  - 特点：关注宏观趋势和重大风险，时间宝贵
  - 需求：简明扼要的总结和明确建议
  - 使用频率：每周1-2次

- **企业管理人员**：企业公关、市场部门负责人
  - 特点：关注品牌相关舆情和竞争对手动态
  - 需求：及时预警和应对策略建议
  - 使用频率：每天1次

**次要用户**：
- **研究人员**：高校、研究机构的学者
  - 特点：需要详细数据和方法论
  - 需求：可追溯的分析过程和原始数据
  - 使用频率：根据研究需要

- **技术开发人员**：系统运维和二次开发人员
  - 特点：熟悉技术，需要定制化功能
  - 需求：灵活的配置和扩展能力
  - 使用频率：不定期

#### 2.2.2 用户技能水平

- **计算机操作**：中等水平，能熟练使用Web应用
- **数据分析**：初级到中级，大部分用户无需深入技术细节
- **舆情分析**：中级，具备基本概念，需要系统辅助深度分析

#### 2.2.3 使用场景

1. **日常监控**：每天定时生成舆情日报，了解最新动态
2. **专题分析**：针对特定事件或类别进行深度分析
3. **风险预警**：发现潜在风险时及时告警
4. **应急响应**：突发事件发生时快速分析并提供决策支持
5. **历史回顾**：查询历史数据，进行趋势分析

### 2.3 假定和约束

#### 2.3.1 假定条件

1. **数据源假定**：
   - 微博平台API持续可用，数据格式稳定
   - 热搜榜单真实反映用户关注焦点
   - 用户评论具有代表性，可用于舆情分析

2. **技术假定**：
   - LLM服务（GPT-4o-mini）稳定可靠，输出质量满足要求
   - 网络环境稳定，能够支持大规模API调用
   - 硬件资源充足，能够满足并发处理需求

3. **业务假定**：
   - 用户具备基本的计算机操作能力
   - 分析结果仅供参考，最终决策由人工判断
   - 系统输出内容符合法律法规要求

#### 2.3.2 约束条件

1. **技术约束**：
   - 必须使用LangGraph框架实现多Agent协作
   - 后端必须使用Python开发，前端使用Vue 3
   - 数据库使用MongoDB存储结构化数据，ChromaDB存储向量数据
   - LLM必须兼容OpenAI API格式

2. **性能约束**：
   - 单次任务完成时间不超过30分钟（取决于数据量）
   - 系统支持至少5个并发任务
   - 前端页面响应时间不超过2秒
   - WebSocket实时推送延迟不超过1秒

3. **成本约束**：
   - LLM API调用费用控制在合理范围内
   - 数据存储成本可扩展
   - 服务器资源按需配置

4. **法律法规约束**：
   - 数据采集需遵守平台服务条款
   - 用户隐私保护符合《个人信息保护法》要求
   - 内容审核符合《网络安全法》规定
   - 系统运行需获得必要资质和许可

5. **时间约束**：
   - 项目开发周期：6个月
   - 试点运行期：1个月
   - 正式上线时间：2026年Q2

## 3. 需求规定

### 3.1 功能需求

本系统采用模块化设计，主要功能模块包括：数据采集、数据处理、智能分析、报告生成、系统管理五大模块。

#### 3.1.1 数据采集模块

**功能编号**：F-01
**功能名称**：热搜数据采集
**优先级**：高

**功能描述**：
自动从微博平台采集热搜榜单数据和相关用户评论，为后续分析提供数据基础。

**详细需求**：

1. **热搜榜单采集**
   - **输入**：采集时间范围、分类筛选条件
   - **处理**：
     - 调用微博API获取实时热搜榜（Top 50）
     - 提取词条名称、排名、热度值等字段
     - 按设定的时间间隔（如每小时）采集一次
   - **输出**：存储到MongoDB的`hot_trends`集合
   - **数据格式**：
     ```json
     {
       "word": "某事件热搜词",
       "rank": 1,
       "num": 1234567,
       "category": "社会",
       "collected_at": "2026-01-19 12:00:00"
     }
     ```

2. **评论数据采集**
   - **输入**：热搜事件ID、采集数量（Top 15帖子）
   - **处理**：
     - 根据热搜词条搜索相关热门帖子
     - 采集每个帖子的标题、内容、作者、发布时间
     - 采集帖子下热门评论（Top 200条）
     - 提取评论内容、点赞数、评论者信息
   - **输出**：
     - 帖子数据存储到`weibo_contents`集合
     - 评论数据存储到`weibo_comments`集合
   - **数据格式**：
     ```json
     // 帖子
     {
       "note_id": "1234567890",
       "event_name": "某事件",
       "title": "帖子标题",
       "content": "帖子正文内容",
       "author": "用户昵称",
       "publish_time": "2026-01-19 10:00:00",
       "like_count": 1000,
       "comment_count": 500
     }

     // 评论
     {
       "comment_id": "comment_001",
       "note_id": "1234567890",
       "content": "评论内容",
       "user": "评论者昵称",
       "like_count": 100,
       "publish_time": "2026-01-19 10:05:00"
     }
     ```

3. **增量更新机制**
   - 支持断点续传，避免重复采集
   - 记录每次采集的最后时间戳
   - 对比历史数据，只保存新增或变化的数据

**性能要求**：
- 单次热搜榜单采集时间 < 10秒
- 单个事件的帖子+评论采集时间 < 2分钟
- 支持5个并发采集任务

**异常处理**：
- API限流时自动重试（最多3次）
- 网络超时时间设置为30秒
- 失败记录到日志，不影响其他采集任务

#### 3.1.2 数据处理模块

**功能编号**：F-02
**功能名称**：ETL数据清洗与归并
**优先级**：高

**功能描述**：
对采集的原始数据进行清洗、去重、归并，生成标准化的核心事件数据集。

**详细需求**：

1. **数据清洗**
   - **去除重复**：相同词条只保留一条记录
   - **去除噪声**：过滤广告、垃圾信息
   - **数据标准化**：
     - 统一时间格式为 `YYYY-MM-DD HH:MM:SS`
     - 热度值统一转换为整数（去除逗号）
     - 提取纯文本（去除HTML标签、表情符号）

2. **分类标注**
   - **功能**：为每个热搜词条自动标注类别标签
   - **支持类别**：
     - 社会：社会事件、民生问题
     - 高校：教育相关话题
     - 生活：生活方式、娱乐资讯
     - 科技：科技产品、互联网动态
     - 政治：政策法规、政务动态
     - 其他：无法归入上述类别的话题
     - 综合：不限定类别的全量分析
   - **技术实现**：
     - 使用LLM并行分类
     - 批量处理提高效率（每批10个词条）
     - 已有标签的词条跳过分类
   - **输出**：
     ```json
     {
       "word": "热搜词条",
       "category": "社会",
       "confidence": 0.95
     }
     ```

3. **热度归并**
   - **策略**：精确匹配累加
   - **规则**：只有词条名称完全相同的热搜记录才累加热度值
   - **处理流程**：
     ```
     原始数据：
     2026-01-19 10:00  "某事件"  100000
     2026-01-19 11:00  "某事件"  150000
     2026-01-19 12:00  "某事件"  200000

     归并结果：
     "某事件"  总热度 = 450000
     首次出现 = 2026-01-19 10:00
     类别 = "社会"
     ```

4. **Top N筛选**
   - 按总热度值降序排序
   - 取Top 20作为核心事件集
   - 存储到`core_events`集合

**数据质量要求**：
- 数据完整率 > 99%（关键字段无缺失）
- 分类准确率 > 90%（通过抽样验证）
- 去重准确率 = 100%（无重复记录）

#### 3.1.3 智能分析模块

智能分析模块是系统的核心，包含5个AI Agent，采用LangGraph工作流编排，实现协同分析。

##### F-03-1：Agent A - 热度统计

**功能编号**：F-03-1
**功能名称**：热度统计分析
**优先级**：中

**功能描述**：
对ETL处理后的核心事件进行热度统计和排名，生成热度趋势报告。

**详细需求**：

1. **数据获取**
   - 从MongoDB的`core_events`集合读取Top 20事件
   - 支持按类别筛选（如果用户指定了类别）

2. **统计指标计算**
   - **总热度**：事件的所有热搜记录热度之和
   - **平均热度**：总热度 / 出现次数
   - **峰值热度**：单次采集的最高热度值
   - **持续时间**：首次出现到末次出现的时间跨度
   - **热度趋势**：按时间序列绘制热度变化曲线

3. **排名分析**
   - 按总热度降序排列
   - 标注排名变化（上升/下降/持平）
   - 计算排名变化率

4. **输出格式**
   ```json
   {
     "event_name": "某事件",
     "total_heat": 5000000,
     "avg_heat": 250000,
     "peak_heat": 300000,
     "duration": "3天",
     "rank": 1,
     "rank_change": "+2",
     "trend": "上升",
     "category": "社会",
     "time_series": [
       {"time": "2026-01-17 10:00", "heat": 100000},
       {"time": "2026-01-17 12:00", "heat": 150000},
       ...
     ]
   }
   ```

##### F-03-2：Agent B - 观点分析

**功能编号**：F-03-2
**功能名称**：舆情观点深度分析
**优先级**：高

**功能描述**：
对每个事件的用户评论进行深度分析，提取主要观点、情绪倾向、对立程度等信息。

**详细需求**：

1. **Map阶段（单帖子分析）**

   **输入**：
   - 帖子内容（标题+正文）
   - Top 200条热门评论
   - 帖子媒体链接（可选）

   **处理**：
   - **观点聚类**：
     - 识别2-5个主要观点阵营
     - 提取每个阵营的核心观点
     - 估算各阵营的占比
   - **情绪分析**：
     - 识别评论中的情绪（支持/反对/愤怒/同情/担忧等）
     - 计算情绪强度
   - **对立分析**：
     - 判断评论区是否存在激烈争论
     - 识别核心矛盾点
     - 评估对立程度（激烈/温和/和谐）

   **输出Schema**（Pydantic定义）：
   ```python
   class OpinionCluster(BaseModel):
       viewpoint: str = Field(description="核心观点")
       emotion: str = Field(description="情绪（支持/反对/愤怒/同情/担忧等）")
       estimated_ratio: str = Field(description="占比（如：约60%）")

   class PostOpinionSummary(BaseModel):
       opinion_clusters: List[OpinionCluster] = Field(description="观点簇列表")
       conflict_analysis: str = Field(description="舆论对立分析")
   ```

   **并行处理**：
   - 使用线程池并发处理多个帖子（max_workers=8）
   - 超时时间：3分钟/帖子
   - 失败重试：最多2次

2. **Reduce阶段（综合分析）**

   **输入**：
   - 事件的Top 15个帖子的Map分析结果
   - 联网搜索的背景信息（可选）

   **处理**：
   - **事件概况**：
     - 整合所有帖子信息，生成事件摘要
     - 提取关键人物、地点、时间
     - 判断事件类型（突发/持续/发酵）
   - **观点聚合**：
     - 跨帖子整合相似观点
     - 识别主流观点和少数派观点
     - 分析观点分布特征
   - **深度洞察**：
     - 分析舆论演化路径
     - 识别潜在风险点
     - 评估事件影响力

   **输出Schema**：
   ```python
   class EventAnalysisReport(BaseModel):
       event_overview: str = Field(description="事件概况（150-300字）")
       public_opinions: List[dict] = Field(description="公众观点列表")
       depth_analysis: str = Field(description="深度分析（300-500字）")
   ```

3. **事件去重**
   - 使用LLM判断两个事件是否为同一事件的不同表述
   - 如果重复，只保留热度更高的那个
   - 确保最终分析5个不同的事件

4. **联网搜索增强**
   - 集成Tavily搜索API
   - 搜索事件的官方通报和权威报道
   - 作为背景信息辅助分析

**质量要求**：
- 观点提取准确率 > 85%
- 情绪识别准确率 > 80%
- 分析覆盖度 = 100%（每个事件都分析）

   - 识别高风险事件

##### F-03-4：Agent D - 趋势预测

**优先级**：中

   **历史同期检索**：

   - 识别季节性规律（如开学季学生事件高发）

## 7. 故障处理需求

### 7.1 故障类型

#### 7.1.1 网络故障

**现象**：
- API请求超时
- WebSocket连接断开
- 数据采集失败

**处理策略**：
1. **自动重试**：
   - 立即重试1次
   - 指数退避重试2次
2. **降级方案**：
   - WebSocket断线后使用HTTP轮询
   - 无法获取新数据时使用缓存数据
3. **告警通知**：
   - 记录错误日志
   - 发送告警（如配置）

#### 7.1.2 LLM服务故障

**现象**：
- API返回4xx/5xx错误
- 响应超时
- 输出格式错误

**处理策略**：
1. **自动重试**：
   - 最多重试3次
   - 更换参数重试（降低temperature）
2. **降级方案**：
   - 使用规则引擎替代LLM
   - 返回部分结果（如Agent A的输出）
3. **人工介入**：
   - 标记失败任务
   - 通知管理员

#### 7.1.3 数据库故障

**现象**：
- MongoDB连接失败
- 查询超时
- ChromaDB检索失败

**处理策略**：
1. **自动重试**：
   - 短暂等待后重连
   - 最多重试5次
2. **降级方案**：
   - 使用本地缓存
   - 延迟写入（批量提交）
3. **数据恢复**：
   - 从备份恢复
   - 重新采集数据

#### 7.1.4 任务执行失败

**现象**：
- 某个Agent执行失败
- 任务整体异常退出

**处理策略**：
1. **断点续传**：
   - 保存已完成的步骤状态
   - 从失败点继续执行
2. **部分结果**：
   - 返回已完成Agent的输出
   - 生成简化版报告
3. **错误报告**：
   - 记录详细错误堆栈
   - 分析失败原因
   - 提供修复建议

### 7.2 故障恢复

#### 7.2.1 数据恢复

**备份策略**：
- MongoDB：每天凌晨3点全量备份
- ChromaDB：每周全量备份
- 报告文件：实时备份到云存储

**恢复流程**：
1. 停止服务
2. 从备份恢复数据
3. 验证数据完整性
4. 重启服务
5. 验证功能正常

#### 7.2.2 服务恢复

**自动恢复**：
- 进程崩溃：Supervisor自动重启
- 任务失败：自动重试
- 连接断开：自动重连

**手动恢复**：
- 检查日志定位问题
- 修复代码或配置
- 重启服务
- 验证功能

### 7.3 日志记录

#### 7.3.1 日志级别

| 级别 | 说明 | 示例 |
|------|------|------|
| DEBUG | 调试信息 | 函数入参、返回值 |
| INFO | 常规信息 | 任务开始、节点切换 |
| WARNING | 警告信息 | API限流、重试 |
| ERROR | 错误信息 | 任务失败、异常 |

#### 7.3.2 日志内容

**必须包含**：
- 时间戳：精确到毫秒
- 日志级别：DEBUG/INFO/WARNING/ERROR
- 模块名称：如[Agent B]
- 线程ID：异步任务标识
- 消息内容：详细描述
- 异常堆栈：ERROR级别必须记录

**示例**：
```
2026-01-19 12:05:30.123 [INFO] [Agent B] 开始分析事件: "某事件" (Thread: task_20260119_1205)
2026-01-19 12:05:35.456 [ERROR] [Agent C] 审核失败: API超时 (Thread: task_20260119_1205)
Traceback (most recent call last):
  ...
```

#### 7.3.3 日志存储

**文件日志**：
- 路径：`logs/app.log`
- 大小限制：10MB
- 滚动策略：保留最近30天
- 压缩：历史日志zip压缩

**数据库日志**（可选）：
- 表名：`system_logs`
- 字段：时间、级别、模块、消息
- 索引：级别、时间
