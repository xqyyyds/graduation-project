# Agent B 按需搜索改造方案

## 一、背景与问题

### 1.1 当前实现现状

Agent B（舆情深度分析 Agent）采用 **Search + Map-Reduce** 架构：

```
Search（联网搜索）→ Map（观点聚类）→ Reduce（聚合报告）
```

当前 **Search 阶段**是**固定执行**的：
- 每个事件都会触发联网搜索
- 搜索词固定为：`"{event_name} {period_hint} 事件详情 官方通报"`
- 搜索结果作为 `web_context` 传入 Reduce 阶段

### 1.2 存在的问题

| 问题 | 说明 |
|------|------|
| **成本浪费** | 即使数据库已有充足信息，仍会联网搜索 |
| **搜索词固化** | 无法根据事件类型和缺失信息动态调整 |
| **效率低下** | 每个事件都要等待网络返回（2-5秒） |

### 1.3 改造目标

让 Agent B 具备**自主判断能力**：
- 先评估数据库信息是否足够
- 只有在数据不足时才联网搜索
- 搜索词根据缺失信息动态构造

---

## 二、核心设计：预读打分法

### 2.1 设计思想

在正式分析之前，让 LLM 快速"预读"数据库内容，判断是否足够撰写【事件概述】。

**判断依据：能否回答三个核心问题**
1. 事件起因/背景是什么？
2. 核心争议点/冲突是什么？
3. 官方/当事人态度是什么？

### 2.2 架构变化

**改造前：**
```
analyze_event()
  → 固定搜索（每次都执行）
  → Map-Reduce
```

**改造后：**
```
analyze_event()
  → 预读评估（新增）
      ├─ 快速扫描样本数据
      ├─ LLM 判断充足性
      └─ 返回建议搜索词
  → 按需搜索（条件执行）
      ├─ 充足 → 跳过
      └─ 不足 → 搜索
  → Map-Reduce（保持不变）
```

## 三、关键组件设计

### 3.1 数据充足性评估结果

定义一个结构化的评估结果，包含以下字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `is_sufficient` | 布尔 | 数据是否足够撰写事件概述 |
| `missing_info_types` | 字符串列表 | 缺失的信息类型，如：["事故原因", "官方通报"] |
| `suggested_search_query` | 字符串 | 建议的搜索查询词 |
| `reasoning` | 字符串 | 判断理由 |

### 3.2 预读采样策略

为控制 Token 消耗，预读阶段只采样少量数据：

| 数据源 | 采样量 | 处理方式 |
|--------|--------|----------|
| 帖子内容 | Top 3 热门帖 | 每帖截取前 200 字 |
| 评论内容 | Top 10 热评 | 每条截取前 80 字 |

**总 Token 估算**：约 1000-1500 tokens，足够 LLM 做判断

### 3.3 评估 Prompt 设计

采用与现有 Prompt 一致的风格：

```
### ROLE
调查记者的数据评估专员

### GOAL
快速评估素材是否足以撰写事件概述

### INPUT DATA
- 事件名称
- 帖子样本（Top 3）
- 评论样本（Top 10）

### THINKING PROTOCOL（4步思维链）
步骤1：提取已有事实（起因/争议/立场）
步骤2：评估信息质量（事实 vs 情绪）
步骤3：判断充足性（基于事件概述写作要求）
步骤4：构造搜索建议（如果不足）

### OUTPUT
结构化 JSON（符合 Schema）

### SELF-CHECK
- 判断基于实际内容
- 缺失类型具体明确
- 搜索词精准
```

### 3.4 充足性判断标准

基于【事件概述】的写作要求（≥150字，需包含：关键时间节点、冲突爆发点、官方处置动作、媒体定性）：

| 判断 | 条件 |
|------|------|
| **充足** | 能回答 ≥2 个核心问题，且有事实支撑 |
| **不足** | 只能回答 0-1 个问题，或全是情绪宣泄 |

### 3.5 缺失信息类型

预定义的缺失信息类型列表：

```
['事故原因', '官方通报', '事件背景', '处置进展', '责任认定', '各方立场']
```

搜索词构造格式：`{event_name} {缺失信息关键词}`

## 四、按需搜索逻辑

### 4.1 决策流程

```
预读评估结果
    │
    ├─ is_sufficient = true
    │   └→ 跳过搜索，web_context = "暂无网络背景信息"
    │
    └─ is_sufficient = false
        └→ 使用 suggested_search_query 进行搜索
           web_context = get_web_context(搜索词)
```

### 4.2 搜索词示例

| 缺失信息类型 | 建议搜索词 |
|--------------|-----------|
| ['事故原因', '官方通报'] | "{event_name} 事故原因 官方通报" |
| ['事件背景'] | "{event_name} 事件背景" |
| ['处置进展'] | "{event_name} 处置进展 善后" |

## 五、保持不变的部分

### 5.1 Map-Reduce 逻辑

- `_map_single_post()`：单贴观点聚类 —— **完全不变**
- `_reduce_summaries()`：深度聚合报告 —— **完全不变**

### 5.2 输出 Schema

`EventAnalysisReport` 结构保持不变：
- `event_overview`：事件概述（≥150字）
- `public_opinions`：舆论观点列表（≥4项）
- `depth_analysis`：深度分析（≥200字）

### 5.3 现有 Prompt

- `AGENT_B_MAP_TEMPLATE` —— **不变**
- `AGENT_B_REDUCE_TEMPLATE` —— **不变**
- 只新增 `AGENT_B_DATA_ADEQUACY_TEMPLATE`

---

## 六、边界情况处理

| 场景 | 处理方式 |
|------|----------|
| 没有帖子数据 | 直接判断为不足，使用默认搜索词 |
| LLM 调用失败 | 降级为"不足"，默认进行搜索 |
| 搜索失败 | 保持原逻辑，使用空背景继续分析 |

---

## 七、预期效果

### 7.1 成本节省

- 预计 30%-50% 的事件可以跳过搜索
- 节省网络请求和 API 调用成本

### 7.2 质量提升

- 搜索词更精准，根据缺失信息动态构造
- 避免"搜不到"或"搜偏了"

### 7.3 速度提升

- 跳过搜索的事件直接进入分析，节省 2-5 秒
